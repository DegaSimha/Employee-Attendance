# REVIEW.md

The table reviews the supplied starter implementation, before the changes in `app/main.py`.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | It calculates the shift start on the punch-in's calendar day, does not distinguish overnight attendance dates, and tests whole minutes rather than the exact ten-minute boundary. | For a 09:30 shift, test 09:40:00 and 09:40:01; for 22:00-06:00, test an early-morning punch-in on the prior shift date. | Calculate against the record's IST attendance date and compare elapsed seconds to 600 before flooring minutes. |
| 2 | `compute_work_hours` | Python `round` uses ties-to-even, but R4 requires decimal half-up rounding. | Use a duration that produces a half-cent-hour boundary, such as 16,218 seconds (4.505 hours). | Use `Decimal` and `ROUND_HALF_UP`. |
| 3 | `compute_overtime` | It anchors every shift end to the same date and starts overtime immediately, with no 30-minute minimum. | Test 29:59 and 30:00 after shift end, and a 22:00-06:00 shift ending the following date. | Resolve the shift end from the shift start/end and record date, floor elapsed minutes, and apply the 30-minute threshold. |
| 4 | `health` | It returns 200 without contacting MongoDB. | Stop MongoDB and call `/health`; the starter still claims readiness. | Execute a MongoDB ping and return 503 when it fails. |
| 5 | `EmployeeIn` / `create_employee` | The request model does not enforce contract formats, lengths, valid dates, valid shift times, or distinct shift start/end values. The stored creation time is also naive. | Submit malformed employee codes, email/date/time values, identical shifts, and overlong fields. | Add Pydantic v2 validation and write a UTC server timestamp. |
| 6 | `create_employee` | A pre-insert duplicate check alone is racy, and the starter does not establish a unique index. | Send concurrent creates for one `emp_code`; both can pass the check. | Create a unique `emp_code` index at startup and translate duplicate-key errors to 409. |
| 7 | `list_employees` | The offset is `page * page_size`, and `total` counts all employees instead of the filtered set. Results are not explicitly sorted. | Request page 2 and a department filter; rows are skipped and totals are wrong. | Use `(page - 1) * page_size`, count the applied filter, and sort by `emp_code`. |
| 8 | `punch_in` | It fails unclearly for an unknown employee, accepts unapproved statuses, interprets timestamps in the host timezone, does not validate epoch milliseconds, and derives the date without the overnight rule. | Use an unknown employee, invalid status, seconds-looking timestamp, or overnight early-morning punch. | Validate request values and employee existence; convert epoch milliseconds to UTC, then calculate the IST shift date. |
| 9 | `punch_in` | The duplicate check is check-then-insert without a uniqueness guarantee, and its response includes an internal Mongo id. | Race simultaneous same-day punch-ins or inspect the response for `id`. | Enforce the natural key with a unique compound index, handle duplicate-key errors, and serialize only contract fields. |
| 10 | `list_attendance` | It fetches the entire collection into Python before sorting and paging, and returns a generated `id`. It also does not validate a reversed date range or enforce deterministic tie ordering. | Exercise a large collection, inspect response keys, request `date_from > date_to`, and create multiple records on one date. | Apply filters, count, sort, skip, and limit in MongoDB; validate date bounds and omit ids from serialized output. |
| 11 | Punch-out | The starter has no punch-out endpoint. | `POST /attendance/punch-out` has no implementation. | Add eligible-record lookup, time-span validation, stored-derived-value calculation, and atomic conditional close. |
| 12 | Regularization | The starter has no correction endpoint or append-only audit mechanism. | `PATCH /attendance/{emp_code}/{date}` has no implementation. | Add status/time validation, recompute derived fields, record only actual changes, and condition the write on the original record state. |
| 13 | Employee monthly analytics | The starter has no monthly aggregation or handling for joined dates, weekends, half-days, leave, or stored derived values. | Call the monthly analytics path or compare a weekend/mid-month joiner result. | Build an aggregation for log metrics and calculate weekday count from the employee's joining date. |
| 14 | Department summary | The starter has no department aggregation; starting from logs alone would omit employees with zero logs. | Include a department employee with no attendance records. | Start from qualifying employees, look up their monthly attendance, and preserve employees without matching logs. |
| 15 | Late leaderboard | The starter has no ranked result, and a simple limit would truncate ties at the cutoff. | Give multiple employees the same total at the rank limit. | Aggregate per employee, use MongoDB competition rank, then filter by rank rather than array position. |
| 16 | Department trend | The starter has no gap-filled daily trend, headcount-by-join-date, or rolling average. | Query a range with a weekend and zero-record weekdays. | Generate calendar days inside the MongoDB aggregation, calculate daily metrics there, and use a seven-row window. |
| 17 | Explain endpoint | The starter has no explain endpoint to expose execution plans. | Call `/admin/explain/{endpoint}`. | Build explain plans from the same query/pipeline builders used by the real handlers. |

Not defects: keeping attendance dates and employee `joined_on` values as `YYYY-MM-DD` strings is intentional in the supplied data model; converting those calendar values to instants would introduce an unnecessary timezone. Reading stored derived attendance values in analytics is also intentional and required by the contract.
